# Operations guide

## Install

Use the setup in the root README. Before startup, set `APP_DOMAIN`, `ACME_EMAIL`, the bootstrap/app/migration database credentials, `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `SESSION_SECRET`, `EMAIL_SIGNING_SECRET`, `FILE_SIGNING_SECRET`, `JOB_SIGNING_SECRET`, and provider vault key material. Set `SES_SNS_TOPIC_ARN` to the exact SNS topic that receives SES configuration-set events; SES webhook ingestion rejects requests when it is absent. Configure SES DNS identity and account production access before enabling tenant sending. Runtime `DATABASE_URL` must name the `APP_DB_USER` role; it is created with `NOSUPERUSER NOBYPASSRLS`. `MIGRATION_DATABASE_URL` must name `MIGRATION_USER`, a separate non-superuser schema owner. URL-encode reserved characters in connection URL credentials and keep `.env` private. Backups and exports contain sensitive donor information and need access control and encryption at rest.

The `db-bootstrap` one-shot service uses the PostgreSQL bootstrap administrator to idempotently create or update the two runtime roles, grants schema access to the migration owner, grants ordinary data access to the app role, transfers existing ordinary public-schema objects to the migration owner, and leaves tenant RLS enabled. The bootstrap role is never passed to the web or worker services. The application role must not have `BYPASSRLS` and must not own tenant tables. The migration role is also non-superuser; it owns schema objects so forced RLS applies to the runtime role. User and membership reads are scoped to a tenant by the application transaction context.

On an existing PostgreSQL volume created before role separation, keep `POSTGRES_USER` and `POSTGRES_PASSWORD` set to the original initialization credentials for that volume. Changing these variables does not rename an existing PostgreSQL role and can prevent health checks or bootstrap from connecting. The bootstrap step updates the app and migration role passwords from `.env` and transfers ordinary public-schema object ownership on each run. Verify `DATABASE_URL` and `MIGRATION_DATABASE_URL` use the new distinct roles before restoring public traffic. For a fresh volume, the example bootstrap role is `donor_crm_admin`.

The Compose services use pinned image tags and named volumes. Their resource ceilings are starting limits for a small VPS, not capacity guarantees. Monitor CPU, memory, PostgreSQL connections, Redis memory, and free disk. Set an alert before the disk is nearly full; backups, database growth, uploads, and exports all consume VPS storage. Tune limits from measured workload.

## Migrations and upgrades

The `migrate` service runs before the web process. Back up before upgrading, review migration output, and stage upgrades against a copy first. Destructive schema changes require an explicit rollback/data restoration plan; PostgreSQL migrations are not automatically reversible. Keep the previous image tag available until the upgrade is verified.

## Backup and restore drill

`ops/backup.sh` blocks public traffic and stops the worker while it captures the PostgreSQL dump and uploads/exports archive. The web container remains available internally only to write the archive. Keep the paired files together and move them off the VPS. Add encryption and retention in the off-host backup destination; the local named volume is not enough if the server is lost.

`ops/restore.sh` stops public traffic and the worker, restores files and the database, then starts migrations and services. The restore overwrites active data. Rehearse against a disposable Compose stack, verify row counts/tenant separation and file access, record elapsed recovery time, then preserve the drill date and result in the operator runbook. No backup is proven until a restore succeeds.

`ops/test-backup-restore.sh` runs an isolated PostgreSQL custom-dump and paired uploads/exports restore drill without Docker. It verifies a restored database file reference against the restored file checksum. `npm run smoke:worker` builds and starts the worker as a separate process against temporary PostgreSQL and a local Redis server, dispatches a signed no-provider outbox event, and checks its tenant-scoped handler completed; set `REDIS_SERVER` if Redis is installed at a different path. These local checks do not replace a Compose restore rehearsal or production recovery-time measurement.

## Secrets and integrations

Only store server-side provider credentials. `src/lib/providers/vault.server.ts` provides tenant/provider/credential-bound AES-256-GCM envelope encryption; inject a base64 encoding of 32 random bytes as `CREDENTIAL_VAULT_KEY`, keep the key ID with the envelope, and retain old key versions until all envelopes have been rotated. The web and worker must receive the same active keyring. For rotation, inject `CREDENTIAL_VAULT_KEYRING` as a JSON map containing both old and new key IDs and base64-encoded keys, set `CREDENTIAL_VAULT_KEY_ID` to the new active version, re-encrypt and verify all stored envelopes, then remove the old key. Never expose plaintext credentials in routes, logs, HTML, or exports. Email preview, explicit approval, consent suppression, SES quota checks and an uncertain-send guard are enforced by the send ledger/worker. SES callbacks require signature verification and exact topic configuration. Rotate `JOB_SIGNING_SECRET` after queued work drains or is re-signed. Codex device-code login is disabled.

The reverse proxy image is built from `Dockerfile.caddy` and runs as UID/GID 10001 without Linux capabilities. It listens on unprivileged container ports 8080/8443; Compose maps these to host ports 80/443 (including UDP/443 for HTTP/3). Fresh named `caddy_data` and `caddy_config` volumes inherit the image's writable ownership. When upgrading existing volumes that were created with different ownership, stop the proxy, back up both volumes, and correct their ownership to 10001:10001 before restarting; do not solve this by running the proxy as root.

## Current limits

The product is under active implementation. Research imports parse caller-supplied 990-PF XML; live source adapters require licensing and are unavailable by default. Stripe Connect and webhook flows are implemented and locally covered, but real provider-account scenarios and production operation remain unverified. Email templates, scheduling, sender/DNS diagnostics, preferences, approvals, and queue delivery controls are implemented; live SES delivery, verified identity setup, and public signed-callback handling still require operator credentials and deployment. File uploads require an isolated private ClamAV daemon via `CLAMAV_HOST` and `CLAMAV_PORT`; production uploads fail closed when scanning is unconfigured or unavailable. Backups still need encryption and off-host handling, migrations do not have automatic rollback, and production Compose/restore behavior requires an operational drill. Staff email verification and invited-member onboarding are implemented, with SES delivery required to exercise them end to end. Review `FEATURE_STATUS.md` and `VALIDATION.md` before opening tenant data to users.
