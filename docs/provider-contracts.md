# Provider contracts

`src/lib/providers/types.ts` defines the canonical TypeScript interfaces and `CapabilityManifest`. Domain entities should store normalized fields and provenance; vendor-specific fields remain in encrypted, retention-controlled provider payloads.

| Interface               | Contract                                                                                                   | Current production behavior                                                                                                                                                         |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PaymentProvider`       | tenant + connected account, minor-unit amount/currency, idempotency key; returns provider intent ID/status | Stripe Connect PaymentIntent adapter is implemented behind the server-side platform key; disabled when absent. OAuth/onboarding and embedded checkout remain incomplete             |
| `OutboundEmailProvider` | tenant, single recipient, sender, content, idempotency key; returns provider message ID                    | AWS SES v2 adapter plus preview/approval send workflow is wired; sender identity and production access are checked before enabling                                                  |
| `ResearchProvider`      | bounded keyword/geography query; every record has source URL, observation time, license, and evidence      | Disabled until a permitted source adapter is configured                                                                                                                             |
| `AIProvider`            | tenant API key and model; returns structured provider output                                               | OpenAI Responses API adapter is implemented with per-request character/output-token caps. No app route or tenant key retrieval flow is wired; Codex device-code mode is unavailable |
| `BlobStorage`           | put/get/delete and short-lived signed download for tenant-scoped opaque IDs                                | Local private filesystem adapter is implemented; object-store adapter is deferred                                                                                                   |

Disabled adapters throw `ProviderUnavailableError`; they never produce a fake success. The test-only adapter file returns synthetic fixture responses and identifies each descriptor with `mode: test`; it must not be selected by production dependency wiring. `StripePaymentProvider` requires an already-authorized `acct_...` value resolved by a server service from tenant integration state; never accept it directly from an untrusted browser. It sends the tenant UUID as Stripe metadata, uses the connected account scope and caller idempotency key, and returns only an intent client secret for Stripe Elements. Do not log that client secret.

`SesEmailProvider` signs SES v2 requests with AWS Signature Version 4 and server-side credentials loaded from the tenant vault (prefer short-lived IAM session credentials). It accepts only the configured sender address and one recipient, tags sends with tenant and idempotency metadata, checks sender verification/account quota before enablement and previews. Sending requires a fresh exact-recipient preview plus owner/admin/marketer approval. Consent and suppression are checked during preview, approval and immediately before each send; sends are rate-limited against the live SES quota. Each recipient has a ledger row and one outbox event. As SES does not guarantee idempotent sends, provider timeout or worker crash after a send begins results in an `uncertain` state and automatic resend is blocked. Plain-text messages include a signed unsubscribe link; link confirmation writes a tenant suppression and revokes consent. Signed SNS events are accepted only for `SES_SNS_TOPIC_ARN`; delivery, bounce and complaint events are replay-safe, and bounce/complaint suppress future mail. The integration is not enabled unless SES reports production access and a verified sender identity.

`OpenAIResponsesProvider` calls only `https://api.openai.com/v1/responses`; its tenant key is passed per call and not retained. It bounds input characters and output tokens, but it does not enforce aggregate tenant spend or user authorization. The route/service layer must authorize tenant access, load/decrypt that tenant's key, apply rate and spend limits, and audit usage before enabling the adapter. Do not use Codex credentials.

`CredentialVault` in the server-only `vault.server.ts` encrypts each credential with a fresh AES-256-GCM data key, then wraps that key using an AES-256-GCM master key. Associated data binds the envelope to tenant, provider, and credential ID, preventing ciphertext reassignment. Keep the key ID alongside encrypted values. Its environment helper supports one key with `CREDENTIAL_VAULT_KEY` or a rotation keyring JSON map in `CREDENTIAL_VAULT_KEYRING`; set `CREDENTIAL_VAULT_KEY_ID` to the active key. Rotate by loading both versions, calling `rotate`, verifying every stored row, and only then removing the old key.

## Tenant integration and AI APIs

`GET /api/v1/integrations` returns configured/enabled status and non-secret metadata for the active session tenant. `PUT /api/v1/integrations/openai` accepts `{apiKey,model,enabled}`. `PUT /api/v1/integrations/ses` accepts `{region,fromAddress,accessKeyId,secretAccessKey,sessionToken?,enabled}`; enabling checks AWS SES identity verification and account production access before encrypted storage. `DELETE /api/v1/integrations/{openai|ses}` removes that tenant's encrypted credentials. These endpoints derive tenant scope from the validated session, recheck active owner/admin membership in the database transaction, and never echo keys. Credential writes require HTTPS in production; demo mode rejects credentials and cannot enable a provider.

Email drafts remain tenant-scoped `workspace_records` with resource `emails`. `GET /api/v1/email` returns current drafts, send readiness and batch status. `POST /api/v1/email/preview` accepts `{emailId}` and returns exact eligible `{id,name,email}` recipients, count, sender, SES quota, a ten-minute one-use preview token, and approval requirement. Eligibility requires explicit `contacts.data.consent === true`, a valid address and no tenant suppression. `POST /api/v1/email/send` accepts `{previewToken,approved:true}` only; it rechecks draft content, consent and suppression, inserts a send batch, one message row and one idempotent `email.send` outbox event per recipient in the same transaction, then returns HTTP 202 with `status: queued`. Recipients added after preview are not silently included. The worker rechecks consent/suppression and uses an advisory tenant rate schedule before calling SES. `GET` on `/unsubscribe/{token}` only renders a confirmation; `POST` applies the opt-out. `/api/v1/webhooks/ses` rejects everything except signed SNS `Notification` messages for the configured topic ARN, and unsupported SNS subscription confirmation messages are not followed.

`POST /api/v1/ai/summary` accepts `{question}` and returns a read-only summary answer and token counts. The server aggregates contact counts by stage and sends only those counts plus the question to the model, never contact names or email addresses. Owner/admin membership is rechecked, each attempt reserves against per-tenant 5/minute, 100/24-hour and 100,000 input-character/24-hour caps, and `ai_usage` stores prompt hash, model, bounded usage and outcome without storing prompt or response text. Per-request limits are 8,000 input characters and 512 output tokens. These are request-volume limits, not a hard monetary spend cap.

## Filesystem adapter

`FilesystemBlobStorage` constructs paths as `<UPLOADS_DIR>/<tenant UUID>/<object UUID>`, never from the submitted filename. Current accepted types are PDF, JPEG, PNG, WebP, and plain text, up to 25 MiB. It checks a small file signature, uses private directory/file modes, stores media type metadata, and emits HMAC-signed app download paths with expiries capped at one hour. The route that resolves the app URL must verify the signature and separately verify user membership and object tenant before streaming. Malware scanning, authenticated streaming route, and retention/deletion workflows remain follow-up work.

## Outbox and queue semantics

Domain mutation and outbox insert belong in one database transaction. The worker enumerates the global tenant directory, then selects each tenant's unprocessed rows inside a transaction with `app.tenant_id` set, so FORCE RLS remains active. It signs the complete event (including tenant, outbox id, type, payload, and idempotency key) with `JOB_SIGNING_SECRET`, publishes a BullMQ job using the outbox UUID as stable `jobId`, then sets `processed_at`. Here `processed_at` means successfully handed to durable Redis-backed queue storage; BullMQ job state is execution truth. A repeated poll is safe because the job id is stable. Handlers reject invalid job signatures and must use `withTenantTransaction` for RLS-scoped database access, reauthorize the tenant operation, and use the event idempotency key before external side effects.

Failed dispatch increments `attempts` and stores a bounded, redacted error string. Consumer jobs retry with exponential backoff and remain in BullMQ after success or failure for operator inspection. Unknown event types fail visibly. Rotate `JOB_SIGNING_SECRET` only after draining or re-signing pending queue jobs. Never mark a job complete merely because it was enqueued. Queue monitoring/remediation UI and alerting are not yet implemented.
