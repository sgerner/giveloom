# Implementation plan

Status is deliberately conservative. A route sketch, fixture, or documentation contract does not count as a working feature. Each phase advances only when its schema, authorization, service, user flow, failure path, and meaningful tests exist. `FEATURE_STATUS.md` is the current feature-level ledger.

## Foundation and sequence

1. **Foundation:** Docker Compose, health and resource controls, Node adapter, theme/brand shell, migrations, identity and tenant membership, RLS, audit, PWA, CI, monitoring, backup/restore. Empty/repeat migrations, tenant isolation tests, and a paired PostgreSQL database/files restore drill have passed; production-like Compose and off-host restore verification remain open.
2. **CRM:** contacts/organizations/households, duplicate review and reversible merge, import preview/rollback, activities/tasks, consent, segments, and role checks. Preserve the current app contract (`contacts { id, name, email, stage, tags }`; gifts/campaigns/tasks/prospects retain their documented shapes).
3. **Giving:** immutable gifts and correction events, Stripe tenant account connection, server-created PaymentIntents/SetupIntents, embedded Stripe elements, verified webhook ingress and receipts. Do not accept browser redirects as payment evidence.
4. **Communications and workflows:** suppression, tenant-authorized email providers, consent-aware templates and delivery, then versioned BullMQ workflows with transactionally written outbox events, idempotent consumers, retries, and visible failures.
5. **Prospect research and relationships:** licensed source adapters, import provenance and use restrictions, identity review, explainable scoring, typed affiliation and personal edges, consent-aware introductions. IRS filings do not constitute a comprehensive individual donor directory.
6. **AI and reporting:** tenant API-key provider only, authorized retrieval and preview/confirmation for writes, explicit budget and audit; reports reconciled against ledger events.
7. **Expansion:** public donor portal, events, peer fundraising, accessibility/performance, upgrade and restore documentation.

## Delivery checks

- Before migrations, reconcile [the ERD](docs/ERD.md) with service types and compound tenant foreign keys. Migration files must apply from an empty database and a prior supported release.
- Implement one vertical slice at a time: schema, tenant authorization, service, route/UI, meaningful tests, and operator documentation.
- Run formatting, Svelte/TypeScript checks, unit/integration tests, and critical Playwright journeys after relevant increments. Never mark a feature `tested` or `shipped` until its acceptance checks pass.
- Demo data must be labeled synthetic and must never send real email, create live payments, or call paid research.
- Operations must include migration/rollback instructions, a consistent database/files backup, off-host backup guidance, and a restore drill.
